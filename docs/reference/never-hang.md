## Never-Hang Constraints (non-negotiable)

The proxy sits inside an agentic loop: whatever stalls a turn stalls the agent.

- **A restart is a stream killer, so the drain waits for a true zero first, then picks its moment.** `docker restart` cuts every in-flight SSE mid-body and each client reports `Connection lost mid-response` — that agent turn is lost. An initial 30-min measurement (2026-08-23, 906 samples) saw `activeStreams` never reach 0 (min 1; p50 5, p90 7, mean 5.1) and produced the first design — relative target, no zero wait. A ~2-day population probe (2026-08-25, 92 364 samples) corrected that window: **min 0, 4.62% of samples at zero, P(zero within 300s) = 57.5% (73.4% within 600s)** — the floor IS zero, lulls are just brief (mean 5.9s). `scripts/claudish-drain.ps1` therefore holds a true-zero wait for the first 300s (`$target` stays -1, only `activeStreams==0` fires — on the FIRST zero sample, no confirmation: confirming costs a whole lull), then falls back to the adaptive stage for the ~43% unfavorable draws: observed minimum as target, relaxed by one every 30s so the wait ends on a chosen moment rather than on the cap. Replay of the 2026-08-23 samples through the adaptive stage alone: **mean 5.19 → 3.65, worst case 10 → 6**; relaxing once per poll instead of every 30s gives the gain straight back (4.67). Budget: `$MaxWaitSec=600` (300s zero-wait + ~300s adaptive) — the 04:00 daily restart can afford 10 min. Even so, **restarting less often remains the mitigation that matters more than draining better** — `ClaudishDailyRestart` (04:00) ran the drained wrapper from 2026-08-23 (first drained restart: 08-24 04:00, logged in `~/.claudish/drain.log`), but **no scheduled daily restart is left on the fleet** — per machine: po-2023's was **disabled 2026-09-05** (user UAC), the hub po-2025's ran until **08/10** (last `daily-0400` → `OUTCOME success` 07:31 local) and was **deleted 08/10 10:09:58 local** (user UAC batch v2). The user arbitrated "no daily restart", so this is a settled decision, not an open question — settled in #280's direction 2, which also names what replaces the task: **the watchdog's proactive restart (uptime ≥ 11 h, quiet window 03:00-06:00 local, `$ProactiveRestartHours`/`$QuietHourStart` in `claudish-watchdog.ps1`) is the single nightly restart source**, so a machine with uptime to burn still restarts about once a night in practice. That de-facto nightly restart has a visible price: on 10-10 the relay po-203 (watchdog decision 01:01:05Z) and the hub po-2025 (decision 01:02:02Z, 84 s drain to zero, `docker restart` 01:03:37→01:03:47Z — hub `watchdog.log`) both restarted proactively within three minutes — scheduling coincidence, not a coordinated gesture — and the hub's stop-start interval cost 2× 502 on the WAN edge (01:03:42/46Z, attributed in #407). Both states are declared in `docs/deployment/fleet-state.md`. A `$null` count means *no signal* (proxy down, or image predates #37) and must degrade to an undrained restart, never to an unbounded wait.
- **The proxy itself never breaks a stream**, and that invariant is what makes the above diagnosable: there is no `controller.error()` anywhere in the proxy's **production** sources under `packages/cli/src` (test harnesses legitimately call it — see the filter below), and every terminating path emits `message_stop` — including `finalizeWithError` on an upstream socket death and the relay passthrough on a hub death. Corpus re-check 2026-09-20, ai-01, **1017 captured `resp-*.sse` over 10/08→19/09** (3.7× the original 277 sample): **1016 of 1016 non-empty responses carry a terminal `message_stop`** — and the 1017th is **0 bytes**, so it carries no events at all and is classifiable in neither direction. That empty-capture class is the trap, not the invariant: a `grep -L 'event: message_stop'` reports it as "1 response without a terminal event", which reads exactly like a never-hang violation. So a client-visible mid-response drop is never the stream logic; the socket died underneath it.

  ⚠ **Checking the `controller.error()` half needs a filter that drops comments *and* tests — and this paragraph's own earlier filter was insufficient.** The instrument, re-measured 2026-09-20 on `main`:

  ```bash
  grep -rn 'controller\.error(' packages/cli/src --include='*.ts' \
    | grep -v '\.test\.ts' | grep -v ':[0-9]*: *\(//\|\*\)'   # → 0
  grep -rn 'controller\.close(' packages/cli/src --include='*.ts' \
    | grep -v '\.test\.ts' | grep -v ':[0-9]*: *\(//\|\*\)'   # → 24  (positive control)
  ```

  The two weaker filters both mislead, and the numbers this paragraph used to quote have drifted while the invariant has not: a **bare** grep now returns **8**, not the "2 hits, both prose" written here earlier (3 comments — `stream-registry.ts:13`/`:91` plus `anthropic-sse-s4a.test.ts:65` — and 5 real calls); **comment-excluding alone returns 5**, every one of them in a `*.test.ts` harness that deliberately errors a `ReadableStream` to simulate a mid-stream socket death, which is *how the never-hang behavior is tested*. So a reviewer following the filter this doc prescribed got **5** and had grounds to report the invariant broken — the exact false conclusion the paragraph exists to prevent (raised against PR #166 on 2026-09-20, then refuted by re-running the same filter on `main`: identical 5, so not the PR's). **Before concluding from a count, run the same filter on the merge base** — a hit class that predates the change is not the change's. The 24 `close()` calls are the positive control: they prove the filter still matches the pattern rather than silently matching nothing. A doc that invites a check owes the check its instrument — and owes it a scope (`production sources, tests excluded`), since an unscoped number goes stale the first time a legitimate new class of hit appears.

- **`stream: false` must return a single JSON `message`, never SSE.** `/compact` is the real-world caller; SSE back to it surfaces as `"API returned an empty or malformed response (HTTP 200)"`, the session can no longer condense, and it eventually overflows and stalls. `ComposedHandler.handle()` buffers the already-translated SSE via `collectAnthropicSseToMessage()`. The trigger is exactly `payload?.stream === true` (mirrors `request-logger.ts`); anything else buffers to JSON. The collector **never throws** — a broken or empty stream degrades to a well-formed message with an empty text block.
- **A failed web search/fetch must never stop the agent** — every backend path degrades to well-formed text. No throws, no hung streams.
- **Never gzip the SSE response** — gzip buffering risks a hang. Request body only, WAN only.
- **A stream admitted with 200 that never produces a first useful event is confined, not held** — during the 14/09 deepseek-flash scheduler incident, mute-but-keep-aliving streams held hub slots ~900s each (46 streams / 19 pending at peak). `withFirstUsefulEventWatchdog` (wired in `ComposedHandler.handleStream`, all SSE formats, not ollama-jsonl) cancels the upstream after `CLAUDISH_FIRST_EVENT_TIMEOUT_MS` without a first `data:` line (default 300s, `0`=off, re-read per request — in a container that means the process re-reads its own env: a NEW value enters only at the next **recreate**, and only because compose carries the name, #310); the parser's existing synthetic finalization then ends the client turn cleanly. The window covers the FIRST useful event only — a `: keep-alive` comment or `event:` line is not one — so legitimate long thinking (whose deltas are data events) can never trip it.
- **A retried stream needs its OWN watchdog — the original wrap has already disarmed.** The wrap above clears its timer on the first `data:` line and *never rearms*; an in-stream error chunk (`data: {"error":…}`) is itself such a line, so by the time it triggers a transparent retry the protection is gone, and a bare `doFetch()` replacement would be unbounded — a mute-but-200 retry upstream then hangs the client exactly as #108 confines. `boundRetryUpstream()` (`first-event-watchdog.ts`) wraps the closure once in `handleStream`, so all three retrying lanes inherit it; non-ok/bodyless responses pass through untouched, and `ollama-jsonl` is excluded from both wraps (that wire has no `data:` lines, so wrapping it would fire on every healthy stream). Measured in review of #137: with a 1 s window in force and the wrapper removed, the client stream was still open after 6 s; with it, the turn terminates at the window. Corollary for any future recovery path: **a guard that disarms on a signal cannot protect what that same signal triggers.**
- **An upstream death before any client-visible event is recovered, not finalized (#170).** Never-hang was already satisfied by `finalizeWithError` — the turn ended cleanly — but it ended on a *notice instead of an answer*, and nothing had been forwarded that would prevent re-issuing the request. `anthropic-sse.ts` now re-forwards on both death shapes (`reader.read()` throwing, **and** a graceful `done` having emitted nothing — `docker stop` on the upstream produces the second), gated by the same predicate #65 uses for policy refusals: `!sawMessageStart && highestSeenIndex === -1 && !lastBlockOpen`. Past any of those three a replacement stream would duplicate what the client holds. Bound + kill switch: `CLAUDISH_PREVISIBLE_REFORWARD_MAX` (default 2 = the `[400, 1200]ms` ladder, `0` = off, re-read per stream), on its own counter so it composes with the policy retry without either becoming unbounded. The relay supplies the closure (it passed none before — the opts comment read `absent = inert (relay, tests)`), header-bounded and **wrapped in `boundRetryUpstream()`**: the relay bypasses `ComposedHandler`, so there is no outer watchdog to inherit and a mute-but-200 replacement would hang the client — mutation-proven, wrap removed ⇒ the stream was still open at 20 s. A re-forward is a recovery attempt, never a liveness measurement: **no `markFail`**, same separation as the #80 part 2 connect retry. Accepted knowingly: the upstream may have generated tokens that never reached us, so a re-forward can bill twice — the bound is what keeps that cheap. Driver, 2026-09-20: 13 hub container restarts in one morning (a remediation for a forwarder wedge that restarts cannot fix) cut every in-flight SSE on every relaying machine at 9-13 `activeStreams` each; **the fleet-wide turn loss came from the remediation, not the wedge.**
- **A policy refusal is retried, then surfaced labeled — never bare, never silent (#65).** `invalid_prompt`-class refusals (exact code on OpenAI-shaped wires; usage-policy message pattern on anthropic-compat wires that carry no code — Z.AI/MiniMax/Kimi) get a bounded transparent retry of the *identical* body (`[1000, 3000]ms`, max 2), fired **only while nothing client-visible exists** — stricter on `anthropic-sse`, which also requires no forwarded `message_start` since that event comes from upstream there and a retry past it would duplicate it. A persistent refusal becomes `[Upstream policy refusal — invalid_prompt: …]` + `end_turn` + `message_stop`. The classifier deliberately excludes transport errors, quota walls and rate limits, so it can never divert a subscription wall away from `isQuotaExhaustion`. `[PolicyRefusal] lane=… model=… provider=… attempt=… action=retry|surface` (forceConsole) is the countable marker for #41/#60. Before this, `openai-sse` **dropped in-stream `{"error":…}` chunks entirely** — a refusal on most providers' lane surfaced as an unexplained "empty response".
- **The failover notice never throws** — a thrown error would turn a working condensation into a failed one.
- **Strip inline `role: "system"` messages** (Claude Code v2.1.153+ injects them, e.g. system-reminders) and merge into the top-level `system` field — for `anthropic-sse` in `composed-handler.ts` and for the OpenAI path in `openai-messages.ts`. Z.AI, MiniMax and Kimi reject anything but `user`/`assistant`.
