## `bun run test:strict` (#175) — full mechanics

**`bun run test:strict` (#175) is how a review gets an opposable verdict from a noisy suite.** The systematic failing population is machine-dependent (PATH corruption left by earlier files, `mock.module` leakage, live endpoints, real defects) — its live count lives in each machine's gitignored `.test-strict-baseline.json`, never in this file (a derived count here has drifted on every capture since). The strict runner executes the suite **bounded and scoped to `packages/cli/src`** (`--timeout 15000` per test + a 420 s wall-clock kill, because bun's timeout covers tests, not hooks — an unbounded run looped >35 min on 2026-09-29; a bare `bun test` also executes any compiled `dist/`, whose fixture-resolution failures are build artifacts, not a test population — measured 2026-10-01: 9 → 52 fails with zero source changes), parses the failing population keyed `file > describe > test` (two files hosting the same describe path are two entries — a name-only key collapses them and hides a new red behind a same-named baseline entry), synthesizes a named entry per module-load death (`# Unhandled error` block → `file: load error #N`; bun 1.3.13 **and** 1.3.14 double-count one such death into BOTH its `fail` and `error` summary counters, so accounting is `entries === max(fail, error)`), and **refuses a verdict** (exit 3) whenever the parsed entries cannot account for bun's own counters or the `Ran N tests across M files` line is absent (truncated output) — a parser blind to a failure shape is how a file dying at import turns into a false green. Comparison against the baseline is by **reproduction, never by count**: fresh entries trigger exactly one confirmation re-run, and only names present in BOTH runs are regressions (exit 1) — a deterministic new red cannot hide behind flaky slots, and a fail that does not reproduce is noise whatever its count. Baseline fails that vanish are reported as improvement; ENV-GATE manifests are consolidated into one end-of-run block. First use on a machine: `bun run test:strict -- --learn`, then re-run to compare. **A learned baseline is a snapshot, not an instrument — re-learn it after any land that removes a cause of load-time death.** ⚠ **Commensurability is per workflow, not per repo**: `release.yml` installs `bun-version: latest`, while the fork's test workflow (`.github/workflows/test.yml`, #570) deliberately pins **1.4.0**. Seats measured 2026-10-21: ai-01 1.3.13, po-2024 1.3.14; 1.4.2/1.4.3 reported on others. A seat on a different bun from the CI run it compares against is not commensurable — a bun-only defect is green in one and red in the other (measurements: #391). Classes 2/2b (stale contract, win32 defect — TEST-15) stay red and stay in the baseline by design; a static pin in `env-gate.test.ts` refuses ever gating them.

## bun test traps — an in-process `Bun.serve` mock dies after a `node:http` server has lived in the process (#593, #604)

**Never mock HTTP through `Bun.serve` in a test file that can run after a proxy route test.** Measured 2026-10-23 on win32 bun 1.3.14 **and** ubuntu-24.04 bun 1.4.0, from a 30-line standalone repro plus a two-file in-suite repro:

- Once **any `node:http` server** has lived in the `bun test` process, **every `Bun.serve` created afterwards is unreachable**. The real proxy listens through `@hono/node-server`, so each `proxy-server-*.test.ts` route test is a poison source; a *live* hono server poisons too, a closed one heals nothing.
- The poisoned fetch does not fail — it succeeds with Bun's default page: `200 text/plain` `"Welcome to Bun! To get started, return a Response object."`. A JSON parser downstream reports `SyntaxError: Failed to parse JSON`, which is what the CI signature looked like for three weeks. A `node:http` client **hangs**, a raw `net.Socket` connection **hangs**.
- Irrelevant to the outcome: hostname (`127.0.0.1` / `localhost` / `0.0.0.0`), fixed vs ephemeral port, `server.stop()`, `closeAllConnections()` + `close()`, shutdown order, and whether the mock or the hono server came first in the *same* file. A single file run alone is green — no `node:http` server has lived in that process yet, which is exactly why this class never reproduced in isolation.
- **The fix is not a workaround for a Bun bug to be re-tested each release**: stop depending on in-process dispatch. `packages/cli/src/test-support/stub-fetch.ts` exports `installStubFetch(handler)` / `hangUntilAborted(req)`, which answer the same wire semantics as a server (status, headers, JSON/SSE bodies, abort on the client's own `AbortSignal.timeout`) with no socket. Files migrated by #604: `handlers/shared/mcp-searxng-client.test.ts`, `handlers/shared/web-search-executor.test.ts`. The pin in the former (`the mock transport is a fetch stub, not a Bun.serve`) fails loudly if someone reinstates a serve-based mock there.
- A **standalone script** (`bun run path/to/file.ts`, e.g. `fork/server/relay-e2e.ts`) is its own process and is **not** exposed — the poison needs a `node:http` server in the *same* process. `node:http` mocks (`fork/server/relay-keyless-forward.test.ts`) are the safe class too: they are reachable, and they are not victims of the trap.

Second bun trap, encoded in the same helper: **awaiting an `AbortSignal.timeout(n)` abort inside `bun test` hangs forever when that timer is the only pending wakeup**, and a handler promise that never settles suspends the runner at exit. `installStubFetch` keeps a `setInterval(…, 5ms)` alive for the duration of the guarded promise, and `hangUntilAborted` rejects off the request's own abort event instead of returning a forever-pending promise.
