## `bun run test:strict` (#175) — full mechanics

**`bun run test:strict` (#175) is how a review gets an opposable verdict from a noisy suite.** The systematic failing population is machine-dependent (PATH corruption left by earlier files, `mock.module` leakage, live endpoints, real defects) — its live count lives in each machine's gitignored `.test-strict-baseline.json`, never in this file (a derived count here has drifted on every capture since). The strict runner executes the suite **bounded and scoped to `packages/cli/src`** (`--timeout 15000` per test + a 420 s wall-clock kill, because bun's timeout covers tests, not hooks — an unbounded run looped >35 min on 2026-09-29; a bare `bun test` also executes any compiled `dist/`, whose fixture-resolution failures are build artifacts, not a test population — measured 2026-10-01: 9 → 52 fails with zero source changes), parses the failing population keyed `file > describe > test` (two files hosting the same describe path are two entries — a name-only key collapses them and hides a new red behind a same-named baseline entry), synthesizes a named entry per module-load death (`# Unhandled error` block → `file: load error #N`; bun 1.3.13 **and** 1.3.14 double-count one such death into BOTH its `fail` and `error` summary counters, so accounting is `entries === max(fail, error)`), and **refuses a verdict** (exit 3) whenever the parsed entries cannot account for bun's own counters or the `Ran N tests across M files` line is absent (truncated output) — a parser blind to a failure shape is how a file dying at import turns into a false green. Comparison against the baseline is by **reproduction, never by count**: fresh entries trigger exactly one confirmation re-run, and only names present in BOTH runs are regressions (exit 1) — a deterministic new red cannot hide behind flaky slots, and a fail that does not reproduce is noise whatever its count. Baseline fails that vanish are reported as improvement; ENV-GATE manifests are consolidated into one end-of-run block. First use on a machine: `bun run test:strict -- --learn`, then re-run to compare. **A learned baseline is a snapshot, not an instrument — re-learn it after any land that removes a cause of load-time death.** ⚠ **The repo pins no bun and CI installs `bun-version: latest`: a seat on an older bun is not commensurable with CI** — a bun-only defect is green in CI and red locally (measurements: #391). Classes 2/2b (stale contract, win32 defect — TEST-15) stay red and stay in the baseline by design; a static pin in `env-gate.test.ts` refuses ever gating them.
