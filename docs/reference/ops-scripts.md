## Nightly compaction and the watchdog (`compress-captures.ps1` · `claudish-watchdog.ps1`)

nightly 7z compaction + GDrive backup (02:47 — moved off 04:17 on 2026-08-20: the 60-70 min run collided with the 04:00 container restart) · health check, proactive restart, hang recovery. **It is armed on the hub (po-2023) and running**: 661 log lines, a write every 15 min, and a logged proactive restart at 03:01 on 2026-09-01 (measured by po-2023, 2026-09-01). The earlier claim here — *never armed on any machine, verified 2026-08-23: no `Get-ScheduledTask` entry, 4 log lines from 31 May* — **was wrong on both of its legs**, and each leg is a trap worth keeping: (a) the documented install is `/ru SYSTEM` (header line 10), and a non-elevated `Get-ScheduledTask` / `schtasks /query` is **blind to a SYSTEM task** — it exits 1 with no output, indistinguishable from absence; (b) `$LogPath` and `$StateFile` are hardcoded to `C:\Users\jsboi\.claudish\` (lines 17, 31, 154), so on any machine whose operator is not `jsboi` the log is written to a directory that does not exist — **counting its lines measures nothing there**. Verified on myia-ai-01, 2026-09-02: `C:\Users\jsboi` is absent, and whether the watchdog runs on that machine is therefore **still unknown** — neither check can answer it without elevation. ⚠ The hardcoding is deliberate (under SYSTEM, `$env:USERPROFILE` is the *system* profile, not the operator's), so replacing it with `$env:USERPROFILE` would break the one install that demonstrably works. Since #37 it classifies probe failures (429/402/529 → DEGRADED, no restart) and only restarts proactively in the 03:00-06:00 quiet window. **2026-09-20 ×2 (po-2025): Docker Desktop localhost-forwarder wedge** — port 3000 LISTENING, HTTP dead on loopback ONLY, published `0.0.0.0` binding serving (WAN/ARR survived both episodes, every local client died up to ~7h; container restarts were useless ×13, host reboot was the only lever, and the wedge followed container-restart events by minutes both times). **A first attempt at automating recovery caused a worse outage than the one it targeted; it was withdrawn the same day (reverted in `cb3e690`/`cb4f214`), then rebuilt with the guards and tests it never had.** `105a2c8`/`2c4d12c` moved the watchdog/drain probes onto a per-machine `base-url.txt` and added a loopback-watch plus a `Restart-DockerEngine` escalation. At 13:18 it fired on a **real** wedge (`[::1]:3000` dead while the serving path answered a full tool-call stream — third occurrence that day, ~20 min after an engine restart), killed the Docker backend and the WSL VM, then **could not relaunch Docker Desktop** (`Impossible de trouver un paramètre correspondant au nom « LogonType »`). The host was left with no engine at all — every workspace `ConnectionRefused`, on this machine and on clients pointed at it — until a manual relaunch. Strictly worse than the wedge, which leaves 127.0.0.1 and the LAN serving. The root cause outlives that attempt and is worth knowing on its own: **`Register-ScheduledTask` has no `-LogonType` parameter** — it belongs to `New-ScheduledTaskPrincipal` — so the Docker Desktop relaunch inside `Start-DockerEngine` **has never worked on any machine**, on `main`, for its whole existence. It always threw, its own `catch` swallowed the throw, and it logged the reassuring "could not launch Docker Desktop". That single latent defect explains both the 13:18 outage and the 2026-08-29 double reboot: every path that stops the engine has been unable to restart it. Three lessons, all structural: (a) **a remediation that tears a component down must be proven able to rebuild it before it is allowed to tear anything down** — the teardown half was tested, the rebuild half never was, and the verification that was performed (probe does not fire when healthy, 4 addresses at 200, one cycle exit 0) could not have caught it; (b) changing the probe from `localhost` to `[::1]` silently broke the opt-out guard `if ($loopbackUrl -ne $ProxyUrl)`, which disarmed the watch **only because the two strings were equal** on a machine with no `base-url.txt` — once the probe became `[::1]` they could never be equal, so the watch armed on every machine, including ones that never opted in; **a guard expressed as a string comparison between two values that merely happen to coincide is not a guard**; (c) the **detection** is sound and is the only part worth rebuilding — `[::1]` dead while the serving path answers is the exact signature, confirmed three times in one day — and it is the only part that ships: **there is no actuator at all** (#172 AC4). **What ships now is a detector and nothing else** (`scripts/lib/claudish-engine.psm1`, a testable module both the watchdog and the drain import, + `scripts/tests/*.Tests.ps1`, 101 Pester tests in the two suites touched here). The terminal verdict of the wedge path is `escalate` — a log line telling the operator **not** to restart the container, because 13 restarts proved it cannot help. **Zero engine, container or service actions anywhere in that path**, and a static AST test enforces it: a reviewer greps the wedge functions and finds no `Restart-*`, no `Stop-*`, no `-Verb RunAs`, no `docker stop|restart|kill` (the test carries a positive control, because a detector that silently matches nothing proves nothing — injecting a `Restart-Service` into the escalation branch makes it fail naming `Invoke-LoopbackWedgeWatch:543 Restart-Service`). The discriminant is what makes the verdict safe to act on: **`[::1]` dead while 127.0.0.1 *or* the LAN answers is a forwarder wedge; all three families dead is the hub itself** and belongs to the hang path, where a restart *is* the fix — mislabelling that as a wedge would tell the operator to stand down during an ordinary outage. Gated **off by default** on an explicit opt-in file (`<ClaudishHome>\wedge-watch.enabled` containing `enabled`), checked **before any probe runs**, so a machine that never opted in is not even measured; an empty or wrong-content file does **not** arm — the previous guard armed on an accidental string equality. **Every unknown fails safe**: no opt-in file, no visible `[::1]` listener, a throwing probe — all route to "do nothing". With no `base-url.txt` and no opt-in file, behaviour is byte-identical to before on every machine, which is the state of the entire fleet today (verified on the production hub 2026-09-20 14:16: a full cycle under 5.1, exit 0, **prod log delta 0**, and the watch emitted no line at all). `Test-EngineRelaunchReady` survives as the preflight for the *pre-existing* `Start-DockerEngine` — which is where the `-LogonType` defect lived — and is reachable only from that path, never from the wedge path. Since #185 it is ALSO exercised during a HEALTHY cycle (`Invoke-RelaunchPreflightWatch`, called right after the wedge watch): the #181 execute probe needed the Desktop GUI up while its only call site required it down, so it was structurally unreachable in production — the healthy cycle is the only place it can run. ⚠ **Its first live exercise (po-2025, 2026-09-21 11:02Z, #199) refuted the "invoking it is a free no-op second GUI instance" premise**: the relaunch task's action IS the GUI executable, so its instance stays Running for the GUI's lifetime, and `MultipleInstances=IgnoreNew` makes the scheduler REFUSE the second start (0x800710E0) *before the action runs* — no new process ever appears. Control comparison produced by production: the same task SUCCEEDED at the 20/09 19:47 recovery (GUI down; processes born 19:47:11–18) and was REFUSED at 21/09 11:02 (GUI up). Two rules follow (#199): (1) **read `LastTaskResult` as `[long]`, never `[int]`** — every real Windows failure HRESULT has the high bit set, an `[int]` cast THROWS, and the check degrades to `execute:ERROR` hiding the code from you (the unit suite missed it because its only failing fixture was `result=1`, Int32-shaped, and the test helper itself was `[int]` — a harness that shares the code's type assumption is blind to the code's type defect); (2) **0x800710E0 + task State=Running is `execute:SKIPPED(already-running)`**, `Ready=$true`, reason "no fresh exercise performed" — neither a pass claimed nor a failure invented — while the SAME code with no live instance stays `FAILED` (the state guard, on a `$TaskStateReader` seam, is what keeps that mapping from swallowing a genuine refusal; decimal `execute:FAILED(result=N)` tokens unchanged). **#205 then INVERTED the execute condition**: invoking while the GUI runs returns 0 by **single-instance forward** — the born process is a renderer child of the live GUI (measured po-2025 21/09: parent = pre-existing GUI, `--type=renderer`; zero processes born in the 7 h 50 before the probe), so a GUI-up `execute:OK` proves "the scheduler can start the action", never "the action can raise a cold engine", which is the exact class `-LogonType` hid — **every GUI-up `execute:OK` ever obtained is a weak green, not citable as proof**. Since #205: GUI running → `execute:SKIPPED(gui-running)`, `Ready=$true`, "no fresh exercise performed", **not invoking at all** (also stops the resident renderer); GUI absent → the measured invoke, which cold-starts the engine — the only branch where the measurement means anything, and precisely when a relaunch might be needed. **The gui-running SKIP does NOT consume the daily probe** (`relaunchProbeDate` unconsumed, ranks with the THROW branch): on a GUI-autostart machine a consuming skip would certify a daily probe that never measured anything — the same false green one level up. `SKIPPED(already-running)` (#199) stays a measured verdict and keeps consuming. **Default-OFF on its OWN consent file** (`<ClaudishHome>\relaunch-preflight.enabled`, review of #188): the gate is read before anything else, so a merge changes nothing on any machine until an operator creates the file — deliberately NOT shared with `wedge-watch.enabled`, since that consent covers HTTP GETs while this one registers a scheduled task and launches an elevated process, and one consent must not silently carry the other (`Test-ClaudishOptIn` holds the token semantics once; both wrappers are pinned from both sides by mutation). Rate-limited to ONE measured verdict per UTC day (state field `relaunchProbeDate`) — Docker Desktop / Windows updates are weeks apart, so daily catches drift within a day without the 96/day churn; a measured verdict consumes the day (a failed probe escalated every cycle would be noise), a THROW does not (retries next cycle, logged as 'not measured', never as a fault). Failing verdict = `RELAUNCH-PREFLIGHT FAILED` + `ESCALATE` log lines, zero action, under its own AST guard with positive control (no Restart-*/Stop-*/wsl/-Verb/docker stop|restart|kill, and no Invoke-ClaudishDrainedRestart/Start-DockerEngine by indirection). Two environment traps found while building it, each of which had already produced a wrong answer: (i) **production runs Windows PowerShell 5.1**, not pwsh 7 (`schtasks /tr "powershell …"`), and `http://[::1]:3000/health` returns **HTTP 400 under 5.1 and 200 under pwsh 7 at the same instant** — so a `== 200` check invents a wedge on a healthy machine under the only interpreter that matters. A wedge is **no HTTP answer at all**; any status code proves the pipe is alive (`Test-HttpAlive`), the suite is run under **both** interpreters, and a parse guard pins the scheduled-task scripts to 5.1-compatible syntax (`??` / `?.` / ternary are a production-only parse failure there — `CaptureUtils.psm1` is pwsh-7-only by design and is the one documented exception). (ii) **`Win32_ComputerSystem.UserName` is empty under RDP** (it reports the console session only) and `quser` output is **localized** — only the session-name column (`console`, `rdp-tcp#N`) is a stable literal, so that is what the interactive-user resolution keys on. ⚠ Also measured and still true: **a loopback probe must name `[::1]` explicitly, never `localhost`** — `wslrelay` owns `[::1]:3000` alone while `com.docker.backend`'s `[::]:3000` wildcard keeps serving 127.0.0.1 and the LAN, and .NET 5+ (pwsh 7) falls back IPv6→IPv4 fast enough that a `localhost` probe reports healthy straight through the outage, while a Node client resolving `::1` first takes an immediate `ConnectionRefused`. **`networkingMode=mirrored` is a tested dead end** (same day): it removes `wslrelay`, and with it `[::1]:3000`, turning an intermittent loopback wedge into a permanent one — every `localhost`-naming client dead, 2 host reboots. It does **not** stop the service: the LAN path served real tool-call streams throughout. The measurement that said otherwise was `Get-NetTCPConnection -LocalPort 3000 -State Listen` returning **empty**, which is **invalid under mirrored** (sockets live in the mirrored WSL netns and the Windows TCP table never enumerates them): empty means "not visible", never "not serving" — the same class of error as counting armed cascades by name instead of by value. And a one-shot elimination test on a critical path carries its **rollback automatic on failure**: that one logged `ROLLBACK RECOMMENDED` and stopped there, so the outage ran until a human read the log

## Drained restart and recreate (`claudish-drain.ps1`)

**restart without dropping agent turns.** Run it standalone in place of `docker restart`, or dot-source it for `Invoke-ClaudishDrainedRestart` — which needs **`-Recreate -EnvFile <path>`** to deploy, since a restart reloads neither the image nor `.env`. `-EnvFile` is mandatory with `-Recreate` and fails fast if missing: docker compose interpolates every `${VAR:-}` from that file, the hub's real one lives outside the compose dir, and the compose dir's own `.env` holds only `CLAUDISH_PROXY_KEY` — a bare recreate emptied every `CLAUDISH_FAILOVER_*` (2026-09-07). Since #141 the refuse is stronger: an env file that **exists but carries no armed `CLAUDISH_FAILOVER_*` while the live container does** is also refused (an env file can be present and still gut the cascades — it merely lacks them); since #304 the armed count **discriminates**: only the four `<ROLE>` cascade names are an armed state, so a knob-only file (`ARM_AFTER=2` etc., injected since #304) no longer masks a gut — a knob is runtime policy, not a cascade. `install-sidecar.ps1` preserves runtime-policy lines on rewrite and `-RebuildEnvFromContainer` recovers an armed state that lives only in the container. **Since #372 the drain derives its TARGETS from the env file, and the guard refuses on an absent container**: on a sidecar, `-Recreate -EnvFile` alone used to drain, guard and attest against the hub defaults (`claudish-proxy`, `:3000`) while compose recreated the machine's real container — measured ai-01 2026-10-06, file=1 container=0 where the 0 was an ABSENT container, so the #141 guard fail-opened and could never refuse. The env file's `CLAUDISH_CONTAINER_NAME` / `CLAUDISH_HOST_PORT` (written by `install-sidecar.ps1`) now derive `-ContainerName` / `-ProxyUrl` when neither was passed explicitly (explicitness read at SCRIPT level — at function level an operator's explicit value only ever flows in as a dynamic default), an explicit value DISAGREEING with the file refuses before any gesture (exit 1, both values named — draining one container while recreating another), and the detached child re-runs the check idempotently with the forwarded derived values. A `docker inspect` MISS is likewise refused: no signal, never "0 armed". Pins: resolver unit matrix (derivation, idempotence, both refusals, hub positive control) + inspect-miss refusal + a real-child e2e proving the guard inspects the FILE's container, `scripts/tests/claudish-drain.Tests.ps1`, both interpreters. **Since #306 an opt-in admission freeze closes the decision→action gap**: the drain is passive, so streams starting in that window (measured ~18 ms) are uncounted and a restart cuts them anyway — with the operator's consent (`<ClaudishHome>\drain-freeze.enabled` containing the literal token `enabled`, same `Test-ClaudishOptIn` bar as wedge-watch/relaunch-preflight, `-FreezeClaudishHome` to point elsewhere) the drain writes `<ClaudishHome>\drain-freeze` right **after the wait, before the gesture**, and the proxy answers NEW `/v1/messages` + `/v1/chat/completions` + `count_tokens` admissions with **503 + `Retry-After: 15`** (`overloaded_error`) — BEFORE the relay branch, since a frozen admission must not be forwarded either (the forward would die mid-body at the local restart). In-flight streams and `/health` are untouched; `/health` **publishes `admissionFreeze: "flag"|"no-consent"|"no-flag"|"expired"`** and the drain reads it right after arming: `FREEZE armed — proxy confirms` → the window line is real; anything else → `FREEZE NOT HONORED (proxy=<reason>)` and the gesture carries on unfrozen — because the drain's home and the container's bind mount are three independent settings, and a VM clock skew can expire a fresh flag on sight (review 03/10: the drain's own FREEZE line attested what the drain wrote, not what the proxy saw, and a Pester case logged "admissions frozen 22s" with no proxy listening). `<reason>` distinguishes **three failures, not two**: a value from the enum is a mount/clock mismatch ("drain home and container mount differ?"); **`absent`** means the proxy ANSWERED but publishes no `admissionFreeze` field — a pre-#306 image, i.e. exactly what the FIRST freeze-capable `-Recreate` on each machine probes (the container it is about to replace), and the hint there names it ("proxy predates #306 — freeze takes effect on the NEXT deploy", not a mount suspect); `$null` → `no-signal` means /health never answered (review D3: reading the absent field as `flag` was the false-attestation vector of that first deploy, pinned by its own Pester case with the field omitted from the shim). The wrapper's `finally` clears the flag on every exit and logs the window line **only when the proxy confirmed**, and the proxy **ignores any flag older than 900 s** (mtime, not bytes — `DRAIN_FREEZE_MAX_AGE_MS`; the flag is posed after the wait, so the bound covers the ~244 s gesture worst case with ~3.7× margin) so a drain killed mid-gesture cannot freeze a machine forever. Without the consent file the flag is inert: zero behavior change, the default everywhere. ⚠ **Since #318 the freeze reaches RELAYED clients too**: the gate marks its 503 `x-claudish-drain-freeze: 1`, and a relaying sidecar passes a marked 503 to the client exactly as #299 A does for a relayed 529 (no `markFail`, no local replay, and `Retry-After` preserved across the rebuild — it used to be dropped for every relayed non-streaming error). An UNMARKED 503 keeps the fallthrough: a hub's own death is a real 503, and body-sniffing cannot discriminate (real provider overloads emit the same `overloaded_error` shape — the explicit header is the whole discriminator). Safe in both rollout orders: a pre-#318 relay image falls through on a marked 503 as today, and a #318 relay facing a pre-marker hub sees no marker and falls through too. Tests: `proxy-server-drain-freeze.test.ts` (route-level incl. the `/health` field and `count_tokens`, mutations X/C/O proven) + engine/drain Pester suites incl. a shimmed-`/health` confirm/mismatch/deaf/**absent-field** quad (mutation on the confirmation read → exactly the NOT-HONORED trio red)

**Pre-gesture failover-events tick (#368).** Right after the freeze arming and before `$restartAt`/the gesture, the drain runs one tick of `failover-events-collect.ps1` against the **old** container — a recreate destroys its `docker logs` corpus and any restart resets the failover state, and the window between the last scheduled PT15M tick and the gesture is exactly when the proxy re-arms and walls (the #347 gap). The tick is a **best-effort passenger, never a gate**: it runs detached-visible via `Start-Process` with its own `.out/.err` captures (`drain-failover-tick-<stamp>.*` under the drain's home), bounded at `-FailoverTickTimeoutSec` (default 120 s — the drain never waits on a wedged collector; the default fits inside the proxy's 900 s freeze expiry with the ~244 s gesture worst case), and **every failure shape is swallowed-and-logged**: collector exit ≠ 0 (`FAILOVER-TICK collector exit <n> … swallowed, drain proceeds` — its own `NOT MEASURED` / held-watermark semantics intact, a held watermark never blocks the gesture), timeout kill (`FAILOVER-TICK killed after <n>s bound`), and a missing collector path (`FAILOVER-TICK skipped`). A collector absent on the machine degrades to the skip line, zero behavior change. The drain never reads the collector's state back — no dependency in either direction (#347's non-goal honored). Mutation-proven: with the wait bound removed (`WaitForExit(-1)`), the wedged-collector pin goes red (kill line absent + the run outlives its bound) while the drain still completes — a green run without the mutation is not evidence. Tests: the `#368` Describe in `scripts/tests/claudish-drain.Tests.ps1` under both interpreters.

**Detached launch for agent callers (`-Detach`, #312/#338).** A killed caller is the one case no rollback can cover (worst case ≈12.5 min), so agents never run the drain inside a capped tool call but through `powershell -ExecutionPolicy Bypass -File scripts\claudish-drain.ps1 -Detach -Reason <why> [-Recreate -EnvFile <path>]`: the script relaunches itself as a hidden child (always `powershell.exe`, the interpreter the scheduled tasks run) with **every argument quoted per the Windows argument rule** (5.1's `-ArgumentList` join quotes nothing — the unquoted form killed a detached launch silently on 02/10, measured on one machine, two others suspected, #312), captures the child's stdout+stderr to per-run `drain-detach-<stamp>-<pid>.{out,err}.log` under `<ClaudishHome>` (7-day retention), and returns on the child's own handshake — a `START pid <pid>` line the child writes **before any network or container call**, matched **only over the bytes appended after the launch** (an old `START` line naming a reused pid can never fake life; a foreign drain.log writer — the 04:00 task, the watchdog — is never taken for the child). **exit 0** = child alive, then poll for the first `OUTCOME` line **after** that `START` (OUTCOME lines carry no pid; older ones belong to past runs; every `drain.log` line carries a timestamp prefix `[ts]` + space, so poll with an **unanchored** grep — `grep 'OUTCOME'`, never `grep '^OUTCOME'`, which matches nothing and makes the poll hang forever); **exit 3** = no drain is running — child died (rc + stdout/stderr tails + stderr path printed) or the launch itself failed; relaunching is safe; **exit 4** = no `START` line within `-DetachStartupTimeoutSec` while the child **may still be running — do NOT relaunch** (a second drain would race the first; inspect the stderr capture named in the output). Known limit, loud by design: a `-Reason` value starting like a parameter name (`-Recreate …`) kills the child at binding — exit 3 with the binding error in the stderr capture, never a silent no-op. ⚠ **Sandboxes**: `-ClaudishHome` alone is NOT enough — without `-LogPath`, the drain log resolves to `$USERPROFILE\.claudish\drain.log`, i.e. production; pass both, always. `#312` closes only together with **#352** (the same unquoted-join defect at a second caller, `model-version-watch.ps1`).

## Container lifecycle events (`docker-events-collect.ps1`)

**persist container lifecycle events before `docker events` forgets them** (#169): the daemon's ring buffer evicts in ~35 min, so post-hoc attribution of a restart window is impossible — the 2026-09-20 hub incident (5-6 restart windows 03:49Z→09:07Z + recreate 09:13Z) lost every per-window exit code and actor identity, with `RestartCount=0` throughout because the gestures were manual `compose up/start`. One tick = a **bounded `docker events` window** (the process is killed at `-WindowSec`; measured on Docker Desktop 29.8.0 it never self-terminates in any argument form, so the kill IS the close), deduped across windows by `timeNano|action|container` fingerprint, appended as the provider's own bytes to `<ClaudishHome>\docker-events.log` (NDJSON, no BOM — `[System.IO.File]::AppendAllText` with `UTF8Encoding($false)`, because `Add-Content -Encoding UTF8` writes a BOM on 5.1 that corrupts exactly the first event), rotated at 5 MB, with `docker-events-state.json` recording **one tick per run, bounded** — that history is what separates a DEAD collector from a QUIET daemon, the same trap as `grep -L` on a zero-byte capture. 🔴 **It writes lifecycle events ONLY, and that is a security property — never widen the filter back to a bare `type=container` (#192).** That filter admits `exec_create`/`exec_start`, and docker puts the **executed command line** in their `Action` field, so every container healthcheck passing a credential as an argument was appended in clear text to a persisted, rotated log every 15 min — for every container on the host, including other workspaces'. Measured read-only on a live daemon, two 8 s windows over the same `--since`: **313 events / 203 carrying a command line → 0 / 0**, the before-window's distinct actions being `exec_create`, `exec_die`, `exec_start` **and nothing else**. The same missing filter is why it captured **0 lifecycle of 313** — none of what it exists for and all of what it must never touch — and why it could **manufacture its own headline verdict**: healthchecks fire across every container continuously, so ≥5 distinct containers inside 1 s was reachable on a perfectly calm host. Hence the guard runs **before the verdict**, not merely before the write. Two layers answering two different questions: `Get-DockerEventsFilterArgs` (bytes never read) **and** `Select-LifecycleDockerEvents` (never written on a daemon that honors the request differently, testable with no docker at all), with `exec_*` refused **unconditionally, above any allowlist** — the allowlist says which events are *useful*, that says which are never *safe to write down*. `health_status` is deliberately out despite carrying no command line: at one check per 30 s across ~38 containers it would dominate the file and the 5 MB rotation would evict the restart events #169 preserves — a collector whose noise pushes out its own signal has the defect it was built to fix. ⚠ **Anyone who installed the task from the #169 header line before 2026-09-21 should treat the existing log as sensitive** and never paste it into an issue or a chat. Four rules, each load-bearing and mutation-tested: (1) **zero actuator** — an AST test refuses any `Restart-*`/`Stop-*`/`docker stop\|restart\|kill`/`-Verb RunAs` in the file (positive control included), because a collector that "helpfully" restarts is the #173 teardown-without-rebuild shape; (2) **the group verdict never names an actor** — ≥5 distinct containers within 1 s is `shared-cause` (host/daemon), else `targeted`; reading simultaneity as a targeted action was the 2026-08-30 false attribution; (3) **a failed invocation holds the watermark** — advancing on a window that never rendered would silently write off the unread range, and the ambient-culture round-trip (`ConvertFrom-Json` → `[datetime]` → `[string]` → `"09/20/2026 17:34:59"` → docker refuses) broke every tick after the first on the live E2E; `ConvertTo-DockerSinceInstant` renders invariant RFC3339 and unreadable watermarks fall back to the lookback, i.e. toward re-reading. Live proof po-2024 2026-09-20: two ticks around a real `create`+`rm` captured 4 events, and tick 2 showed `events=3 written=2 skipped=1` — the boundary duplicate the overlapping watermark produces, deduped for real. Install: `schtasks /create /tn ClaudishDockerEvents /tr "powershell -ExecutionPolicy Bypass -File <repo>\scripts\docker-events-collect.ps1" /sc minute /mo 15 /ru SYSTEM /rl HIGHEST /f` (+ `-ClaudishHome` where the operator is not `jsboi`). Tests: `scripts/tests/claudish-docker-events.Tests.ps1` (45 as of 2026-09-21; a bare count here goes stale, so treat it as dated) under both interpreters

## Failover event collection (`failover-events-collect.ps1`, #347)

**The hub's `[Failover]` lines (ARMED / DISARMED / walled / failed / DWELL / CLOSED / RECOVERED) live only in `docker logs` and in the failover state's process memory — a recreate destroys both.** The 04/10 window that produced the "408 walls on `haiku[1]`" was lost at the 05/10 07:58:44Z recreate, so the breakdown #331 asks for can no longer be rebuilt; failed cascade steps leave **no** `resp-*` capture either (0 `*kimi*` files on 04/10 and 05/10 although the Kimi step walled both days). Any past-window question about walls died at the next recreate. This collector is where they survive. Pure logic lives in `claudish-engine.psm1` (`#region failover-events collector (#347)`); the glue is the script.

**It writes `[Failover]`-token lines ONLY, and that is a security property** (the #192 lesson, applied from the start rather than after an incident): a `docker logs` window carries request lines, body previews with user text, and Authorization-looking strings. The allowlist is enforced **at the sink** by `Select-FailoverLines`, so it is testable with no docker at all and a line without the marker never reaches the file, whatever the daemon hands back. Refused lines are counted as `Dropped` — a number that says "the filter worked", distinguishable from a simply quiet proxy. Widening to other markers is out of scope: each needs its own allowlist review.

**Zero actuator, deliberately** — collecting is not acting (#173). A static AST test walks the file and refuses any `Restart-*` / `Stop-*` / `Start-*` / `docker (stop|restart|kill|rm|compose)` / `taskkill` / `schtasks /change|create|delete|end|run` / `-Verb RunAs`, with a positive control (9+ injected offenders detected). `Remove-Item` is deliberately **not** in the forbidden set: rotation deletes the collector's own rotated files, filtered by name.

🔴 **The watermark is the instant the window was OPENED, measured BEFORE the docker call — never the return instant (found and fixed during the first live run, 2026-10-05).** The first live comparison did **not** match: **53 ground-truth markers vs 31 collected**. ## Split-brain / ghost-session scan (`split-brain-scan.ps1`, #341)

**Read-only detector answering four questions from the source that is authoritative for each — never from a proxy signal.** Exit codes: `0` = all sources read, no flag · `1` = flags found · `2` = **INCOMPLETE** — a source was unreadable (ProjectsRoot absent, `Win32_Process` query failed, `Get-ScheduledTask` failed), so its section is blind and "no flag" there is a non-verdict; **2 outranks 1** so a cron wrapper never mistakes blindness for clean. Flags carry ISO 8601 UTC timestamps (machine-local times drift across hosts and against the hub's UTC logs). ⚠ A NON-ELEVATED run is blind to SYSTEM-owned tasks (the #169 trap — an empty result is indistinguishable from absence): run elevated for full task coverage; the session and process sections are complete either way.

1. **LIVE SESSIONS** — transcript files under `<ProjectsRoot>\<project>\<session>.jsonl` by mtime. A session id live in **more than one file** is `DUPLICATE-SESSION`, the one shape a split brain leaves behind at rest (a single live session owns exactly one transcript).
2. **PROCESSES** — ONE unfiltered `Win32_Process` snapshot (CIM, not `Get-Process` — the latter fails silently on VS Code "utility-node" parents and invents ghost parents, measured 2026-10-04 po-2024; the snapshot also serves root-ancestor resolution for the display, because a per-process filtered query costs ~1.5 s each). `PROCESS-BURST` flags **what a double-fire IS: the same command line started twice BY THE SAME PARENT** within `BurstWindowSec` (threshold 2, key `(ParentProcessId, Name, command)`, and the arguments are kept in the flag, as for DIRECT). Two successive signatures were refuted by live runs before this one: N same-name processes under one root ancestor was in permanent alarm on a healthy host (one Claude Code session legitimately launches several MCP servers at once, launcher+server `node.exe` each, distinct command lines, and the whole VS Code tree clusters under `explorer.exe` — measured live on ai-01, review #342: rc=1, 20 PROCESS-BURST flags, 2026-10-05 21:06:27Z, one session starting 3 MCPs = 6 `node.exe`); then the bare `(Name, command)` key flagged a **VS Code window restore**: after the 19:56Z host reboot + VS Code update, ELEVEN restored windows each launched an identical 450-char `claude.exe` command under ELEVEN DISTINCT `Code.exe` parents (20:40:17–20:41:54Z) — 35 flags, rc=1 at both interpreters; on that same snapshot the parent-keyed group count is **0**. The parent is what makes a double-fire a double-fire: the same LAUNCHER doing the same thing twice (an extension host opening two identical panels, a `claude.exe` launching one MCP server twice, two identical actions under one Schedule service). A process whose command line is UNREADABLE (access denied, non-elevated) enters **no** equality group — "unavailable" is a rendering, not an identity. A machine-wide co-birth count is printed unconditionally as info, so the same-command-different-parents shape stays visible without being flagged. A claude.exe carries no session id on its command line when VS Code spawns it, so process→session mapping is impossible by design — the session check is (1).
3. **SCHEDULED TASKS** — `Get-ScheduledTask`, **every action of each task** (a first-action-only read misses a direct claude launch hidden as action #2). Flags: `DIRECT-CLAUDE-TASK` (an action launching the `claude` binary without the VBS/PowerShell indirection — repointing/leak signature; prints the executable only, **arguments withheld**, the #192 healthcheck class), `DUPLICATE-TASK` (several actions sharing one target — **count by action target, never by task name**: one task with three triggers prints three identical rows in `schtasks /v` and is NOT a duplicate, measured 2026-10-05 po-2025), and `TASK-NONZERO-RESULT` in ANY state. ⚠ **Result codes are interpreted, never tested by `!= 0`**: the benign set is the **nine codes the code holds** (`0`; `0x800710E0`/2147946720 MultipleInstances=IgnoreNew refused a second start while the previous instance still runs — the healthy overlap shape, #199/#205; and the SCHED_S_* status family `0x41300`-`0x41305` + `0x41325`: 267008 READY, 267009 RUNNING, 267010 DISABLED, 267011 HAS_NOT_RUN — LastRunTime holds the 1999 sentinel, not a ghost, 267012 NO_MORE_RUNS, 267013 NOT_SCHEDULED, 267045 QUEUED — statuses, not failures). `0x41306` (267014 TERMINATED) is deliberately NOT benign — a killed task is a signal. Anything else non-zero flags in ANY state, so a `Ready` task dying on every tick is caught. Read `LastTaskResult` as `[long]`, never `[int]` — every real failure HRESULT has the high bit set and an `[int]` cast throws.
4. **SESSION ROSTER** (#362 P2) — the cron roster rebuilt from the CronCreate traces inside EVERY transcript (`"cron":"<expr>","prompt":"<text>"` + the line's own timestamp; **not bounded by any mtime window** — a stale arming is by definition old). Keyed on (ws-dir, cron, prompt) keeping the LATEST arming per key — `last=` is what separates history from the living. `DOUBLON` (WARN, exit 1): one prompt-root (first token of the prompt) armed from MORE THAN ONE workspace dir with the dirs' latest armings within 48h of each other — the 2026-10-01 double-`/coordinate-adjoint` shape (main + worktree, two simultaneous adjoint loops = the OpenAI burn); a sibling that slid out of the 48h window is HISTORY, and would have flagged on the day. `STALE` (INFO, never flips the exit code): a prompt-root the CALLER declares alive via `-AliveRoles` whose last arming exceeds `-StaleDays` (14) — opt-in by design, an empty list means the class never fires; liveness was asserted by the operator, not measured here. The roster prints roots, dir counts, cadences (capped at 4 + counter — an auto-sized free-text column makes `Format-Table` DROP `NewestLast` beyond the width) and UTC stamps only — **the prompt body is never kept or echoed**.

**Zero actuator** (#172/#185/#192 convention): no process, service, task or file is modified — a detector that acts on what it finds is the #173 teardown-without-rebuild shape. Enforced by an AST guard with a positive control (`Restart-*`/`Stop-*`/`Start-*`/`Remove-*`/`Register-*`/`Unregister-*`/`Set-*`/`Suspend-*`/`Disable-*` cmdlets, `docker stop|restart|kill|rm`, `taskkill`, `schtasks /change|create|delete|end|run`, `-Verb RunAs`), plus the INCOMPLETE pins per source and one pin per flag and per benign shape.

**Tests**: `scripts/tests/claudish-split-brain-scan.Tests.ps1` (both `powershell.exe` 5.1 and `pwsh` 7), fixtures injected by mocking the three OS sources (`Get-CimInstance` — which also throws on any `-Filter`, pinning the single-snapshot rule — / `Get-ScheduledTask` / `Get-ScheduledTaskInfo`); the roster section runs on REAL fixture transcripts written to temp dirs with old mtimes on purpose (the arming must be readable outside every mtime window).

## Content-level split-brain discriminator (`split-brain-content.py`, #41)

**Read-only, capture-side complement to `split-brain-scan.ps1`.** The host scan answers "is a session id duplicated on this machine?"; this one answers the question a host scan cannot, from the hub's own captures: *inside one `session_id`, are two message sequences cohabiting?* (user directive 2026-10-09 — when metadata cannot separate two sequences under one lane, descend to the content). A Claude Code conversation is append-only, so each request's user-message history extends the previous one; the instrument reconstructs those histories and flags sequences that are disjoint **and concurrently alive**.

```console
python scripts/split-brain-content.py --date 2026-10-09 [--session <prefix>]...
```

Method, in order: (1) **harness removal by document frequency** — a user-segment hash present in ≥10% of a broad sample is harness (CLAUDE.md/memory/system-reminders re-injected into every request) and is dropped *wherever it sits*, order preserved; (2) **partition each session's requests by `cc_is_subagent`** (T5 below); (3) **chain by prefix containment** within each partition — B extends A iff A's residual core is a prefix of B's; a compaction replaces the history and legitimately starts a *new, sequential* chain; (4) a **fork** is two chains *inside the same partition whose time ranges overlap*. Chains shorter than 8 residual segments are not counted (T3).

Six measured traps, each of which produced a wrong answer before its fix — the script header documents them in full:

- **T1 — chaining on all segments**: every request opens with the same harness head, so the containment test compares harness to harness and *no request ever extends another* (every chain depth 1, measured on 4021 requests).
- **T2 — stripping a contiguous head is not enough**: the harness injects a *variable* number of blocks whose position shifts between requests; harness blocks survive in the residual core and one thread splits into "concurrent" chains. The tell: every such "fork" was same-machine, same-client IP. Hence document-frequency removal.
- **T3 — short recurring task prompts** (a cron lane re-sends the same opening prompt each epoch) bucket unrelated epochs into one chain spanning hours.
- **T4 — `cc_is_subagent` as a bare grep is always true**: the fleet's own CLAUDE.md documents the 2026-08-10 leak using that literal string, so it is quoted inside nearly every request body. The real flag lives on the `cc_version=…` metadata line — read that line.
- **T5 — a Task sub-agent carries the PARENT's `session_id`** (measured: disjoint requests under one id map exactly onto `cc_version` build `…79e` main vs `…4be` + `cc_is_subagent=true`). One session therefore legitimately holds the main conversation plus one disjoint conversation per concurrent sub-agent — raw content diffing calls that a fork, and a coordinator lane with parallel sub-agents shows dozens of concurrent sub-chains. Partitioning is what separates them; concurrent **SUB** chains are reported for information and are **not** split-brain.
- **T6 — the session id is read by parsing `body.metadata.user_id`** (a nested JSON string), never by a raw regex over the file. A first-match regex grabs a session id **cited inside a message body**: a traffic-analysis session quotes other sessions' ids constantly, so its own requests get attributed to the cited id — and a monotone history chain then arriving "from a second machine" reads as a cross-machine fork. This is the trap memory §23 already recorded for `cc_is_subagent`, biting a second field; the 2026-10-09 run's only flag was exactly this artifact.

**Sampling floor — below it, "clean" is not evidence.** A session is sampled at `--max-samples 150` requests (step = `len // 150`), so on a 4.5k-request session the instrument reads ≈1 request every 30: a chain needs **≥2 sampled requests with cores ≥ `--min-core` (8)**, and two cohabiting chains must each clear that bar *with overlapping sampled spans* to flag. Practical floor: **≳2× step ≈ 60 requests** for the session to be meaningfully observable at all — a session whose sampled residue falls under that reads `clean` by under-coverage, not by proof. Each session line prints its own `step` and that floor (`floor = 2×step`, in requests), so a `clean` verdict always carries its detection threshold on the same line; `--max-samples 0` reads **every** request of every session (step 1, same escape hatch for `--harness-sample 0` on the harness side). Same logic for the harness side: `--harness-df 0.10` presumes a **full-day corpus where no single conversation dominates the sample** — on a corpus where one thread is a double-digit share of the requests, that thread's *own history* segments (they recur in every later request of the thread) cross the df threshold and get stripped as harness. The embedded test pins this on purpose with `--harness-df 1.0` on its 26-request corpus.

**Positive control embedded**: `scripts/tests/test_split_brain_content.py` builds a synthetic corpus — one session_id hosting two concurrently-alive disjoint MAIN chains must be flagged `SPLIT-BRAIN?`, and a *sequential* compaction restart in the same corpus must stay `clean` — plus unit pins for each trap-covered primitive (chain prefix containment, the ≥8-segment floor, overlap vs sequential, T4 line-scoped subagent flag). The 2026-10-09 run produced only a 0; a discriminator that has never fired on real data needs a synthetic fork to prove it still can.

**Verdict run (2026-10-09, hub po-2025, confirmation pass over 45 167 captures, 5 largest CoursIA sessions): 0 split-brain candidates** — the number that stands is from the **post-fix** run; the day's first pass (43 246 captures) flagged one session and that flag is the instrument's most instructive result. It had flagged exactly `3650f974` (the *"Tournee lane trading CoursIA-3, cadence 4 h"* lane): one MAIN chain spanning 16:40→20:09 with five chains starting inside that span — the fork shape, since a compaction would have *ended* the long chain. Machine attribution killed it: 14 of the session's 975 requests came from `myia-po-2025` while 961 came from `myia-po-2024`, and the 14 carried a conversation whose first user text was the user's split-brain directive of that very day — **the analysis session's own requests, mis-attributed by a first-match session-id regex that grabbed an id cited inside a message body** (traffic analysis cites session ids constantly). After the fix (T6: parse `body.metadata.user_id`, never regex the file) the confirmation pass re-read the day at 45 167 captures and returned 0 flags. The other sessions' apparent "two disjoint cohabiting sequences" were main-agent + sub-agent streams (T5); within the main partition every trajectory is a clean compacting sawtooth (zero shared content across each compaction boundary because the summary replaces the history). Corroborates CoursIA's independent GitHub-side finding (no duplicated branches over 386 PRs). Two standing limits: on content alone the instrument cannot separate *two processes on one machine* from *one compacting thread* — that residual ambiguity stays with the host scan (`split-brain-scan.ps1`), which sees the processes; and any flag it does raise is a **candidate to attribute** (machines, launcher, workload line), never a verdict to act on from the capture side alone.

## Bounded instrument passes on the hub host (standing rule)

**Any instrument pass that runs on the hub host (po-2025) is bounded: one invocation, timestamp-filtered, timeout-wrapped — never a loop, never a poll, never a full-corpus sweep when a window filter answers the question.** This covers `docker logs` (one `--since/--until` pass into a file, timestamp awk — not repeated `--since` calls), capture-dir scans (`--since` filter instead of reading the day), `7z l` verifications over 50k-file archives, and **SMB/GDrive reads** — a hung remote read holds its tool slot and, on DriveFS, can wedge the whole G: namespace for minutes (measured 2026-10-16: >120 s reads and 180 s MCP timeouts on the dashboard store, 08:28–09:29Z).

**Why it is a rule and not a habit: instrument bursts are themselves a load signal.** Flap 2026-10-15 and the 2026-10-16 correlation both landed on windows where the hub host was running back-to-back heavy passes (docker image build + three 50k-file 7z verifications at 04:05–04:46Z; G: DriveFS stalls + full-organ git sweeps at 08:55–09:32Z) while sidecars logged AUTONOMOUS transitions. The hub itself stayed continuously up and serving through both (same `instanceId` since 01:03Z, zero log gaps, steady per-machine traffic) — so the causality is **unproven in both directions**, and that is exactly the point: an unbounded pass makes the instrument a confounder of the thing it measures. When a flap investigation lands, the hub-side checklist is: `/health` `instanceId`+`uptimeSec` (continuity), one bounded log pass (gaps + per-machine buckets), host Event Log (System, Error/Warning) — and the investigator's own task timeline in UTC, because local-time mtimes on this fleet (UTC+2) shift every window by two hours and have already sent one attribution attempt down the wrong path.

🔴 **Bounding the invocation COUNT does not bound the I/O VOLUME — and volume is what the hub feels (measured 2026-10-17, self-attributed).** A "bounded" leak pass (one `tool-gap.py` invocation, one 7z extraction, one `native-consumption.py` run — all inside the rule above) still wrote and then deleted **18.5 GB** across 32 356 extracted files in ~35 min of afternoon traffic; the relay logged **6 AUTONOMOUS episodes 14:06→14:33Z** with the exact saturation signature (heartbeat timeouts, deep-probe 2-3× slower, `/health` fast, process alive), zero client impact (the cascade covered, 66 requests served locally), and the dip closed ~3 min after the scratch delete. The rule's three bounds were all honored and the dip happened anyway: a single archive extraction is a full-corpus sweep by another name. **Corollaries**: (a) an instrument pass whose input is a whole-day archive (`native-trend.py --days`, leak passes on `captures-*.7z`) runs **in the calm window right after the nightly compaction** (post-02:47Z), never in daytime traffic — the fleet's tolerance for a pre-dawn dip is categorically higher; (b) extract the **smallest sufficient subset** (pairing needs the req envelopes, but a resp-only question must not unpack the req half); (c) when a daytime pass is unavoidable, say so on the dashboard BEFORE running it, so the next flap investigation finds the confounder declared instead of discovered.



## Log lines that are NOT faults (read before escalating)

**`[Catalog] cache write skipped (unwritable path): EROFS: read-only file system, open '/root/.claudish/all-models.json'` is expected on every compose deployment and must not be re-read as a defect each cycle.** The config bind (`~/.claudish` → `/root/.claudish`) is deliberately `read_only: true` — it carries the provider API keys — so the catalog resolver cannot persist its disk cache. The failure is caught (`catalog-resolvers/openrouter.ts`, the `try/catch` added for #270), the in-memory refresh still succeeds, and resolution degrades to the documented path (dynamic catalog → disk cache → passthrough) with the disk step simply absent inside the container.

**Frequency is per catalog REFRESH, not per container start** (corrected 2026-10-21 after an earlier "1 per start" reading was published): measured 22:39, 04:26, 10:18, 12:21, 18:23, 00:30, 01:01 and **07:11Z** — intervals of ~6 h, and the last one fired **6 h 10 after** the container's `StartedAt` with `RestartCount=0`. One line per ~6 h (or at a restart, which resets the timer) is nominal. Two lines within minutes would be the thing to investigate.

## Review-process analytics (`review-rounds.py`, #445 axis B)

GitHub-side instrument (REST only — GraphQL is chronically exhausted on jsboige, memory `github-graphql-rest-first`; no local corpus needed). Measures the turns metric that replaced the retired "one comment per pushed head" target (coordinator B3, c.6233290794, 17/10): **CR rounds per merged PR**, per calendar month.

**Usage**: `python -I scripts/review-rounds.py --repo jsboige/claudish --months 2 --max-prs 0` — `--months N` window ending at the last complete month, `--max-prs 0` = no per-month cap (default 250), `--selftest` runs the embedded fixture matrix (exit 2 on any wrong count). Bounded by construction: one listing pass page-capped and window-stopped on `updated_at`, one single-page reviews call per in-window merged PR, no bodies fetched — only numbers, states, timestamps and logins leave the API.

**What the columns count**: `merged` = PRs with `merged_at` in the month; `formal rev/PR` = any formal-state review per PR (author's own excluded everywhere); `CR rounds/PR` = CHANGES_REQUESTED events per PR — a CHANGES_REQUESTED dismissed then re-requested by the same reviewer counts twice (that IS a second round on the wire); `PRs >= 1 CR` = share of merges that went through at least one CR; `no review` = merged with zero formal reviews; `1st-rev->merge h` = latency from first formal review to merge (a first review submitted AFTER the merge counts as a review but is excluded from the age — post-merge tidy-up); `trunc` > 0 means a PR returned exactly 100 reviews (review storm) or the listing pager clipped — raise the caps before quoting the month.

**Reading rules**: month buckets key on `merged_at` (UTC) — a PR reviewed in September but merged 01/10 00:30Z is an October PR. The "non-discriminating pin" share of axis B stays MANUAL labeling (pins live in review bodies, which this script does not read) — do not automate it by keyword, that was B3's original sin. Baseline on this repo (run 2026-10-18): Sep 142 merged / 0.00 CR/PR / 141 no-review; Oct 176 merged / 0.13 CR/PR / 20 PRs >= 1 CR / 115 no-review — the review process switched on mid-Oct; two-thirds of merges still land unreviewed.
